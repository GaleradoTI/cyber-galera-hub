- Event links reuse `events.location_or_link` for the external event page, while `online_link` is the meeting URL and `address` is the physical location; this preserves existing rows without schema changes.
- Password recovery uses server-issued one-time codes and the existing Resend connection; locate users by profile email then verify Auth email (fallback to Auth for unsynced changes), and report failed delivery rather than treating it as success.- Phone push uses a push-only worker (public/push-sw.js, no caching) + push_subscriptions; a notifications insert trigger calls /api/public/push/send via pg_net, which re-reads the row by id and dedupes with pushed_at — why: no shared secret needed and the bell stays the single source of alerts.
- The installable app is manifest-only (start_url /login) and the idle-session guard is skipped in standalone mode — why: user wants app users to stay signed in.
- Admin users list reads the admin_users_overview view (profile + roles + badges) via the service role — why: one query instead of three.
- Ambassador access is per user and per action in `ambassador_permissions.areas` (`area` = view, `area:action` = action), enforced by RLS, RPCs and content guard triggers and mirrored by `useAmbassadorCan(area, action)` — why: admins choose each administrative function independently.
- Event attendance is confirmed only through authorized `checkin_by_code`; members see tickets/QR/attendance in their profile — why: check-ins must be trustworthy.
- Notification preferences are applied by a BEFORE INSERT trigger on notifications (muted category = row dropped; push-muted = pushed_at prefilled) using `notification_category()`, mirrored in `src/lib/notification-meta.ts` — why: one gate for bell and push.
- Event reminders run hourly via SQL-only pg_cron (`send_event_reminders`), deduped by `event_reminders_sent`.

- Jobs have `application_type`: recruiters = `interna`, plain members = `externa` + pending approval (DB trigger). Candidate resume data lives in `candidate_profiles` + private `resumes` bucket; contact/resume access only via `can_view_candidate_contact` — why: personal data goes only to the job owner, admins, or recruiters the member opted into.
- Blocked users lose all access (restrictive RLS, role helpers, Auth ban). New tables with RLS need the "Bloqueado sem acesso" restrictive policy.
- Read events with `EVENT_COLUMNS` (never `select("*")`); `online_link` only via `get_event_online_link` — why: only approved attendees and staff may see it. Event registrations are `event_registrations`; `user_event_interests` is history only.
- AI autofill is off unless `public_site_settings.modules.ai_autofill` is true (admin toggle); server functions enforce it with `assertAiEnabled` — why: the AI is not fully working yet.
- Job/event `content_status` is rascunho | publicado | pausado | encerrado (there is no "arquivado").
- Shared visual identity lives in `src/components/brand/ui-kit.tsx` (PageHero, IconTile, StatTile, EmptyState, LoadingState); dashboard headers take icon/area from the sidebar item.
- Drops and Projects are on unless `modules.drops`/`modules.projects` is false; wrap their routes with `withModule` and hide their links. This is UI gating only (data rules unchanged).
